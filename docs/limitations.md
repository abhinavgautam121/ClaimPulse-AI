# Limitations and production considerations

- All claims, patient references, outcomes and contract assumptions are synthetic. Model metrics do not measure real-world denial performance. Balanced classifiers are not probability-calibrated; the UI labels their estimates experimental.
- Submission review flags are editable only before adjudication; after that they are locked to preserve pre-outcome training inputs. Follow-up corrections belong in notes. Original payer/provider/category inputs are not mutable through the update API.
- This prototype cannot guarantee approval, automatically recover money, replace certified coders or make coverage/medical decisions. No HIPAA certification or compliance is claimed.
- One shared synthetic workspace, admin/analyst roles. No organisation tenancy, SSO, MFA, email verification, reset-email flow or invitation service. Do not use this account model for clinical production.
- Demo access intentionally grants synthetic admin access and must be disabled (`DEMO_MODE=false`) outside a sandboxed demonstration. An administrator account can be promoted through the local admin script; no privileged role is accepted from registration requests.
- JWT uses HttpOnly SameSite=Lax cookies with origin checks, eight-hour expiry and token-version logout revocation. Production requires HTTPS, `COOKIE_SECURE=true`, exact CORS origins and hardened gateway policies. WebSockets authenticate at connection time; expiry/revocation is not rechecked on every event.
- Limiter, simulator and WebSocket fan-out are in one backend process. Run one API worker. Multiple replicas require a shared queue/pubsub/limiter (for example Redis) and separate scheduled workers. Rate-limit windows are in process and are not durable.
- CSV/REST/webhook imports are bounded (10 MB for uploads/webhooks, 10,000 rows). They run in request transactions with row savepoints; durable background ingestion queues and distributed job retries are future work. Simulator and scheduled FHIR polling are asynchronous background workers. The UI shows pending/error/success states.
- No claim deletion, payment reversal, insurer recoupment, secondary-payer coordination, line-level payment allocation, real coding library or contract repository. One initial denial record per claim; appeals can have multiple attempts. Seed claim lines carry synthetic category references; they are not clinically meaningful.
- Analytics use database-derived Pandas frames for a reproducible 20,000-record portfolio scale. They are not a warehouse solution; production needs SQL aggregation, incremental materialized views and load/latency benchmarking.
- The scorecard's minimum n=30 rule is a transparency guard, not a statistical fairness guarantee. Priority rules and historical recovery fractions are descriptive; manual overrides are auditable.
- Time filters are submission cohorts. A 90-day submission cohort naturally excludes claims older than 90 days; use a custom range for full A/R ageing. Recovery trends group payments by submission cohort, not cash receipt month (the database recovery view also exposes receipt-month reporting).
- Notification read markers are per user, while synthetic alerts and operational records are shared. Threshold preferences apply when that user refreshes or mutates records, not a multi-tenant notification policy engine.
- CMS returned HTTP 403 during environment verification. NPPES organisation reference lookup was reachable with a required organisation-name criterion. Reference sync is opt-in; neither source is a live private denial feed.
- FHIR R4 adapter accepts only explicitly synthetic resources and same-host HTTPS pagination. Real authorised integrations require separate data governance, credentials, endpoint testing, mappings, consent and legal/security review.
- Source snapshots intentionally omit secrets, runtime datasets and model binaries. Run bootstrap/train after installation. Exported CSV protects spreadsheet-leading formula characters.
- Docker and local deployment validation status is documented in verification.md. External production hosting, a public URL and remote GitHub publication require a deployment/account target; they are not implied by a successful local build.
